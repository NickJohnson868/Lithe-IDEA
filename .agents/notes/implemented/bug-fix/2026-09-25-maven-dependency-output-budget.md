# Agent 笔记：Maven 依赖查询的输出预算与模块范围

状态：已实现

## 先说结论

正常的大型依赖树也可能超过原先的 50 万字符限制，导致依赖加载被提前终止。
依赖查询现在允许捕获 8 MiB 的 UTF-8 文本，由 Rust Core 在启动计划中提供统一预算。
Windows 必须在追加每块输出之前检查累计字节数，不能截断依赖树后把部分结果显示为成功。
查询必须只包含所选模块；mvnd 日志前缀和错误格式不能导致真实依赖被静默丢弃。

## 问题

原实现允许解析 10,000 个节点，却使用与构建控制台相同的 50 万字符预算。
包含较长坐标和版本管理说明的 6,000 行依赖树已经超过旧限制；层级缩进和普通日志还会增加输出量。
命令已经使用批处理及关闭下载进度的参数，因此再关闭下载进度不能解决大型树的问题。
此外，Windows 按 UTF-16 单元计数，Core 按 Unicode 标量计数，非 ASCII 输出的边界并不一致。

## 决策

继续复用 Maven dependency plugin 3.8.1 的详细文本树及已有解析器，保留重复依赖和版本冲突信息。
Core 定义 8 MiB 的 UTF-8 字节预算，依赖启动计划通过 `outputByteLimit` 传给 Windows；普通构建计划不包含该字段。
8 MiB 为常见的数千到一万个详细节点及日志留出余量，同时保留明确的内存上界；它不保证接受任意长度的坐标或日志。

Windows 仅规范化新到的输出块，移除回车后按 UTF-8 字节累计，超过预算便停止进程并清空失败会话。
正确做法是先检查新块是否能容纳，再追加；不要先追加任意大块，也不要每次重新扫描全部历史输出。
新会话重置计数，失败会话的迟到事件不能启动解析。节点数、深度及超时限制保持原有行为。

根模块查询必须显式传入 `-pl .`，避免省略模块时遍历整个 reactor（Maven 多模块集合）。
mvnd 的 `[module] [INFO]` 前缀可以解析，但同一响应出现不同模块的依赖行时必须报错，不能把所有模块合并后归给根模块。
带树形标记却无法解析的行必须报错，不能跳过后显示“无依赖”；真正没有依赖的聚合 POM 仍可返回空列表。

## 考虑过的备选方案

- 只提高前端限制：Core 仍会拒绝相同输出，而且 Windows 与 Core 常量继续漂移，因此不采用。
- 关闭详细输出：会丢失重复依赖和版本冲突信息，改变现有功能，因此不采用。
- 把输出尾部截掉：会把不完整依赖树误报为成功，因此不采用。
- 改用插件输出文件：能分离日志，但需要新增平台临时文件生命周期和读取通道；本次用可复现的大型树用例修正预算，不引入新的资源管理流程。

## 后果

正常的大型树不再受构建控制台预算约束，Windows 和 Core 对多字节文本使用一致单位。
代价是单次查询允许保留更多文本，JSON 编解码期间也存在额外副本；8 MiB 上限仍可能拒绝异常多的日志或超大坐标。
若后续有实际项目仍超限，应保留诊断证据，再评估分离输出文件，而不是持续无依据地增大限制。
