# Agent 笔记：目录加载与工作区通知的交互边界

状态：已实现

## 先说结论

目录展开先改变可见状态，再逐层读取，不等待整个紧凑目录链加载完。空数组代表已经读取过的空目录，只有缺少 children 才代表未读取。同一工作区合并相同目录的请求；收缩、项目切换和关闭后，迟到结果不能重开目录或写回旧项目。

## 问题

原展开操作等待读取与整棵树更新，随后每批并发读取八个目录。空目录会再次读取；展开与收缩没有请求归属检查。首次读取工作区状态容器（Store）还会同步通知其他 React 组件，导致渲染期间更新其他组件。

## 决策

- 文件系统 Store 持有目录请求控制器，显式操作立即展开；读取成功逐层提交，失败允许重试。控制器用代次和展开操作身份检查写回资格。
- 路径索引以不可变的同级节点数组为单位，用弱引用缓存。查找和更新只沿祖先链移动；更新保留无关分支引用。Immer 临时可变对象不缓存索引。
- 预加载在空闲调度后运行，每批最多两个目录，受深度和总目录预算约束。收缩、工作区变更和关闭时撤销资格；原生读取不能中断时也不得接受其过期结果。
- 工作区首次创建 Store 的广播延后到微任务，并合并同一轮的创建通知。实际激活和就绪状态变更保留原生命周期通知；重复的相同就绪状态不广播。

正确做法：点击展开 → 立即显示展开状态 → 读取 → 检查归属 → 局部更新。不要在 Promise 返回后无条件把所有旧展开路径加回集合。

## 考虑过的备选方案

继续提高预加载并发会增加前台 I/O 争用，不能改善点击前等待。取消全部 Store 创建广播会让后台文档和终端观察者无法绑定新容器。每次重建全树索引会抵消局部更新收益，因此只缓存不可变同级数组。

## 后果

展开和收缩不再被连续目录读取阻塞，空目录不会反复请求。未加载目录仍受文件系统读取时间影响；预加载只保证最多两个后台目录读取，不能承诺所有磁盘或远程目录固定耗时。跨 Store 首次通知发生在当前调用结束后，观察者必须以当前容器集合绑定，不能依赖同步创建广播。

## 验证

目录控制器测试覆盖立即展开、展开中收缩、收缩后重开去重、工作区代次失效、迟到失败、紧凑链和预加载并发及取消。路径测试覆盖空目录、祖先结构共享、Windows 和远程路径。注册表测试覆盖延后通知、后台绑定、移除清理及重复就绪。
